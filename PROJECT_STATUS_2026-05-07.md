# Статус проекта на 2026-05-07

## Кратко

За последние 2 дня основная работа была сосредоточена на двух больших направлениях:

1. стабилизация AI-пайплайна, особенно для OpenRouter и нестабильных/free-моделей;
2. улучшение UX вокруг AI-запросов, чтобы врач мог видеть сырой ответ модели, понимать ошибки и не блокироваться во время ожидания ответа.

Текущее состояние проекта: приложение в рабочем состоянии, ключевые AI-сценарии заметно устойчивее, UI не заблокирован во время долгих запросов, а отладка ответов моделей стала значительно прозрачнее.

---

## Что сделано

### 1. OpenRouter: capability-aware логика вместо грубых эвристик

Реализовано распознавание моделей OpenRouter через metadata API OpenRouter:

- добавлен реестр моделей OpenRouter и кэш метаданных;
- профили OpenRouter автоматически обогащаются metadata при создании/обновлении;
- выбор формата структурированного ответа теперь зависит не только от имени модели, а от capability metadata;
- `response_format`, лимиты токенов и часть логики OpenAI/OpenRouter-адаптера теперь опираются на metadata модели;
- снижена зависимость от хрупких эвристик вроде простого поиска `:free` в имени модели.

Основные файлы:

- `src/lib/providers/openrouterModelRegistry.ts`
- `src/lib/providers/profileService.ts`
- `src/lib/providers/types.ts`
- `src/lib/providers/enhancedAIService.ts`
- `src/lib/providers/selector.ts`
- `src/lib/providers/adapters/openai.ts`
- `src/lib/aiServiceCompat.ts`

### 2. XML/JSON обработка для нестабильных моделей

Сделаны существенные улучшения парсинга и repair/fallback-логики:

- XML-парсер стал принимать:
  - теги с атрибутами;
  - `CDATA`;
  - self-closing теги;
  - экранированный XML;
  - альтернативные имена полей для treatment-ответов;
- если модель не вернула корректный XML, добавлен мягкий fallback;
- стало ясно, что часть моделей возвращает свободный reasoning-текст вместо XML/JSON, поэтому парсер больше не считается единственным решением, а используется вместе с UX-обходными сценариями.

### 3. Просмотр сырого ответа модели

Добавлена возможность увидеть первичный ответ нейронки до парсинга:

- кнопка `Сырой ответ ИИ` на страницах `Диагноз` и `Лечение`;
- отдельный диалог для просмотра raw response;
- в результат теперь сохраняются:
  - `rawResponse`
  - `rawResponseFormat`
  - `rawProvider`
  - `rawResponseTime`
  - `wasRepaired`

Это сильно улучшило диагностику model-specific проблем.

Основные файлы:

- `src/components/RawAiResponseDialog.tsx`
- `src/pages/DiagnosisPage.tsx`
- `src/pages/TreatmentPage.tsx`
- `src/lib/aiServiceCompat.ts`

### 4. Новый UX для ошибок AI

Ошибки AI теперь не сводятся к бесполезному `alert`.

Сделано:

- появился управляемый сценарий ошибки через плавающую AI-панель;
- при ошибке пользователь получает:
  - текст ошибки;
  - предложение перейти на более надёжную модель;
  - кнопку открытия настроек;
  - кнопку просмотра сырого ответа;
  - кнопку использования сырого ответа в следующем ручном запросе.

### 5. Повторный ручной запрос с использованием сырого ответа

Если предыдущая модель ответила плохо, но дала полезный медицинский текст, пользователь может:

- сменить модель вручную;
- включить использование сырого ответа как дополнительного контекста;
- снова отправить запрос уже в более надёжную модель.

Для этого:

- в AI prompt добавляется специальный retry-context блок;
- сырой ответ прошлой модели подмешивается только вручную и только по решению пользователя;
- это не ломает исходный сценарий и не включает скрытую автоматическую магию.

### 6. Неблокирующее окно отправки AI-запроса

Это один из самых важных UX-апдейтов.

Теперь окно предпросмотра AI-запроса:

- не является жёсткой fullscreen-модалкой;
- не блокирует приложение во время ожидания;
- перемещается мышью;
- сворачивается;
- может висеть поверх приложения как рабочее плавающее окно;
- не останавливает фоновый AI-запрос при сворачивании.

Фоновое выполнение AI-запроса вынесено в общий контекст консультации, а сверху добавлена плавающая панель статуса AI-задачи.

Основные файлы:

- `src/components/PromptPreviewDialog.tsx`
- `src/components/AiRequestPanel.tsx`
- `src/context/ConsultationContext.tsx`
- `src/components/Layout.tsx`
- `src/pages/DiagnosisPage.tsx`
- `src/pages/TreatmentPage.tsx`

### 7. Automatic Fallback

Была начата и в коде в основном реализована логика более управляемого fallback:

- одна основная модель;
- выбранные пользователем резервные модели;
- остальные профили отдельно;
- автопереход не по всем подряд профилям, а по заданной цепочке.

Это направление требует отдельного живого smoke-test, но базовые изменения уже внесены в типы, настройки и runtime-слой.

Основные файлы:

- `src/lib/providers/types.ts`
- `src/lib/providers/enhancedAIService.ts`
- `src/components/SettingsDialog.tsx`

## Остаточные риски

### 1. Нестабильные free-модели OpenRouter

Даже после улучшений часть free-моделей может:

- игнорировать формат;
- писать reasoning вместо структуры;
- возвращать неполный медицинский ответ;
- вести себя по-разному на диагнозе и лечении.

Это не полностью проблема приложения, а частично свойство конкретных моделей.

### 2. Automatic Fallback

Логика уже продвинута, но её стоит отдельно проверить в живом сценарии:

- основная модель;
- 1-2 резервные модели;
- последовательное падение первой и переход ко второй.

### 3. Полная production-сборка после последних UX-правок

TypeScript build сейчас зелёный.

Полный `vite build` на одном из последних прогонов упирался в долгую фазу `transforming...` внутри инструмента проверки, без явной compile-ошибки. Это выглядит скорее как ограничение инструмента/окружения, но при следующем рабочем заходе стоит ещё раз отдельно прогнать полный `npm run build`.

## Рекомендуемые следующие шаги

### Приоритет 1

Проверить и дочистить `Automatic Fallback` в живом сценарии:

- основная модель;
- резервная модель;
- ещё одна резервная модель;
- понятный порядок перехода.

### Приоритет 2

При желании усилить AI-архитектуру для слабых моделей:

- оставить генерацию как есть;
- при тяжёлых model-specific сбоях использовать более надёжную модель для ручного повторного запроса через уже добавленный raw-response retry-context.

### Приоритет 3

Вернуться к отдельной задаче, которую пользователь уже обозначал ранее:

- хранение AI-настроек/ключей в проекте в более защищённом и удобном виде;
- дальнейшая пригодность для HTML/portable-версии.

## Быстрый контекст для следующего продолжения

Если продолжать позже, логичнее всего стартовать отсюда:

1. открыть настройки AI;
2. проверить сценарий `основная модель -> резервные модели`;
3. прогнать 1 ручной диагноз и 1 ручное лечение:
   - на стабильной модели;
   - на слабой/free-модели;
4. при ошибке проверить:
   - сырой ответ;
   - переключение модели;
   - повторный ручной запрос с использованием raw-response контекста.
